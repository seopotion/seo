# Architecture (Planned)

Intended target architecture for the project. Nothing here is built yet.

## Stack

- **Monorepo**: TypeScript throughout.
- **Backend**: Node.js + Hono, deployed as AWS Lambda functions behind AWS API Gateway. Includes a background worker (the scanner worker).
- **Frontend**: Next.js, hosted on AWS EC2 or ECS (not Lambda).
- **Infrastructure as Code**: AWS CDK (TypeScript). Each Lambda is bundled by CDK `NodejsFunction` (esbuild) at synth time.
- **Async processing**: AWS SQS enqueues scan tasks that trigger the scanner worker Lambda.
- **Package manager**: npm workspaces (no orchestrator yet; Turborepo deferred). `esbuild` at the repo root for Lambda bundling.
- **Database**: MongoDB via the official `mongodb` driver — Zod is the single source of truth for schemas, no Mongoose. See [data-layer.md](data-layer.md).

## Shared Typed API Client

The frontend lives in this monorepo and consumes a **typed Hono RPC client** generated by TypeScript inference from the backend's route types (no codegen). The backend exports `AppType = typeof routes`; a `@shared/clients` package wraps `hc<AppType>`; the Next.js app imports it for fully type-checked API calls that break at compile time if a route's schema changes. See [monorepo-and-api-client.md](monorepo-and-api-client.md) for the full pattern, workspace layout, and testing approach (adopted from the dkn-harbor repo, adapted for Lambda + in-repo frontend).

## Components

- **API** (Hono on Lambda) — serves `/api/v0/core/*`, `/api/v0/setup/*`, and `/dashboard/v0/*` endpoints.
- **Scanner worker** (Lambda, SQS-triggered) — scrapes a customer's website and makes AI calls to generate editable onboarding presets.
- **Frontend** (Next.js) — onboarding/setup flow and the dashboard.

## Key Design Constraints

- **Single Google-auth login path** — chosen to avoid duplicate accounts. Do not add other auth providers without revisiting this rationale.
- **Setup presets are AI-generated *and* user-overridable** — every preset category needs its own read/write endpoint. Never treat scan results as immutable.
- **Scanning is async** — `start_scan` enqueues to SQS and returns; the frontend learns completion by polling `/api/v0/setup/status`, not from a synchronous response.
- **Promo codes are a first-class billing concept** — factor them into the subscription/payment schema from the start, not bolted on later.
