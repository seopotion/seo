# Manual article images

The admin article editor supports up to eight images total, including at most one optional cover
for articles whose `keyword_id` is null. Generated articles retain their existing
image pipeline. Create and save the article before uploading images.

`POST /admin/v0/articles/{article_id}/images/upload` accepts `role`,
`section_heading` (null for cover), descriptive `alt`, `content_type`, and `size`.
Only WebP, JPEG, and PNG files of 1 byte through 100,000 bytes (100 KB) are accepted. Inline
placements use existing, uniquely named H2 sections outside code fences; choosing
an occupied placement replaces that image.

The admin browser accepts source files up to 5 MiB and decodes them with image orientation
applied. Before requesting an upload URL, it converts the image to WebP with transparency
preserved and a maximum 1200 px edge, maintaining aspect ratio without enlarging small
images. It tries quality levels 0.85, 0.75, 0.65, and 0.55, then reduces the longest edge
by 20% and retries from the original decoded image. Resizing stops at a 320 px longest
edge (or the original edge when smaller). Every successful result is measured at no more
than 100,000 bytes. Encoding failures, unsupported WebP encoding, invalid/over-40-megapixel
sources, and images that cannot meet the byte limit fail before any upload URL is requested.
The original file is never sent to S3 by this flow.

The UI reports optimization, upload, and finalization separately and displays the optimized
dimensions and size. Preparation uses the optimized file's MIME type and exact byte count;
the browser sends that same file. Finalization retries reuse the existing token without
re-encoding or re-uploading. Canvas encoding may fall back to PNG when a format is unsupported,
so the optimizer explicitly checks the returned MIME type
([HTML canvas serialization](https://html.spec.whatwg.org/multipage/canvas.html#dom-canvas-toblob-dev)).

The operator-authenticated API issues a five-minute presigned S3 PUT URL and a
15-minute finalization token. Keys are generated by the server as
`articles/{article_id}/manual-{uuid}.{extension}`. The signature binds MIME type,
exact Content-Length, immutable cache headers, and `If-None-Match: *`. The browser
supplies the returned headers and sends the File as its body; it supplies
Content-Length automatically. The conditional write prevents upload URL reuse
from overwriting finalized bytes ([AWS conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)).

`POST /admin/v0/articles/{article_id}/images/finalize` accepts only `upload_token`.
The token uses a purpose-derived signing key and binds the article, org, operator,
bucket, CDN, placement, and previous slot URL. It cannot authenticate an admin API
request. Finalization rechecks article and org existence, manual origin, placement,
and slot limits, then reads the object from S3. It validates actual Content-Length,
Content-Type, the byte buffer's detected image format and dimensions, and a
1200 px maximum edge and 100,000-byte limit. Dimensions come from image headers; the API
does not re-encode files. Existing images and generated-image uploads are unaffected.

A conditional repository write updates structured images, Markdown, and the cover
URL together, preserving concurrent content/image edits. Duplicate finalization
returns the current article without injecting another image. A replaced upload
cannot be replayed to restore its old slot. Inline alt text is Markdown-escaped;
its structured value remains the operator's original text. Manual metadata uses
empty prompt and null model, seed, and generated_at, with measured width/height.
Existing WordPress and static-site publishers consume the same URLs and metadata.

Preparation never changes the article or `images_status`. Finalization leaves
manual images complete even with fewer than eight images. An abandoned browser
upload therefore cannot block publishing. Unfinalized or replaced S3 objects are
retained; this flow does not delete immutable objects or run image generation.

## Removing uploaded images

Each uploaded image on a manual article has a Remove button and confirmation dialog.
Removal saves immediately without publishing. The editor refreshes the image list, count,
cover and Markdown from the response; the freed placement can accept another upload.
Unsaved edits and ongoing image operations disable removal. While removal runs, editing,
uploading and publishing are blocked, and failures leave the preview intact for retry.

`POST /admin/v0/articles/{article_id}/images/remove` accepts `{ url }`, identifying the
exact image rather than its placement so a stale request cannot remove a replacement.
It requires an admin operator and an existing manual article and org. The existing
conditional repository write removes the matching structured image and its Markdown
image references, clears a matching cover URL, and keeps `images_status` complete,
including after removing the last image. Concurrent edits return `article_changed`.
An already absent URL returns the current article without a write or duplicate audit.
Successful changes are audited as `article.image_remove`.

Previously uploaded PNG/JPEG images can be removed regardless of their size or CDN host.
Removal does not require configured image storage or delete the immutable S3 object.
Published copies remain unchanged until an explicit publish/update; future publishing
uses the remaining image metadata and content.

Each stage's AdminFn receives that stack's ImagesBucket and image CDN domain.
Its object permissions are only GetObject and PutObject on `articles/*/manual-*`;
there is no bucket listing, deletion, ACL, or generated-image write permission.
The bucket remains private with CloudFront OAC. Upload CORS permits PUT from the
locally hosted admin app on ports 3000 and 5173 at `http://localhost` and
`http://127.0.0.1`. If the admin app is hosted elsewhere, add that exact origin
to the bucket CORS configuration. Local API development needs IMAGES_BUCKET,
IMAGES_CDN_DOMAIN, and AWS credentials for the intended stage.

The preparation endpoint returns 200 when the upload URL is ready, before any
file bytes are sent. The browser then performs a separate S3 PUT and calls
finalization only after that succeeds. A CORS failure can therefore follow a
successful preparation response. Compare the failing OPTIONS request's Origin
with the deployed bucket CORS allowlist; ports are part of the origin. Browser
network/CORS failures and storage HTTP rejections have distinct UI messages.
